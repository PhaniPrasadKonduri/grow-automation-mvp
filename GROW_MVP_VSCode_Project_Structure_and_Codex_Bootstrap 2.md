# GROW Automation MVP VS Code project structure and Codex bootstrap

Version 1.0 · 30 October 2026 · Companion to the 68-prompt Codex library

## 1. Recommended approach

Use **one repository and one CAP Node.js application**, containing the SAP UI5 frontend under `app/grow`. Keep CAP's conventional `app`, `db` and `srv` roots. Add project-specific folders for deterministic fixtures, tests, engineering scripts and documentation.

This is a modular application, not a microservice estate. Four agents do not require four separately deployed services, databases or repositories. Share the approval, authorization, execution and evidence foundations while keeping their implementation responsibilities clear.

SAP documents applications under `app/`, services under `srv/` and domain/database artifacts under `db/` [S1]. The additional subfolders below are **recommended project conventions**, not mandatory SAP-generated folders.

**Prototype baseline:** 28 screens, 130 named screen actions, 24 common control families, 138 R1 feature representations, 202 proposed BR/TC process records, four agents and five simulated SAP integration touchpoints.

**Technology:** genuine SAP UI5, supported Fiori elements/freestyle patterns, CAP with Node.js, CDS contracts and local persisted demonstration data. HANA Cloud is the production persistence direction; the prototype must start without BTP, HANA Cloud, real SAP credentials or a paid model endpoint.

## 2. How to begin

1. Create a local folder named `grow-automation-mvp` and open that folder as the VS Code workspace.
2. Download the previously generated `GROW_MVP_Codex_Prompt_Library.md` into the repository root, preserving its filename.
3. Save this guide beside it as `GROW_MVP_VSCode_Project_Structure_and_Codex_Bootstrap.md`.
4. Optionally put the Word prototype plan, backlog and BPD in `docs/reference/`. They remain reference artifacts; do not copy binaries into application assets or the deployed UI bundle.
5. Open Codex with access to this repository. Paste the **S00 bootstrap prompt** in Section 12.
6. After S00, run **B00**, then **B01**, **B02**, and continue using the existing prompt library's execution table. Do not sort prompt IDs alphabetically: its order intentionally places B11 after B04 and B12 after B09.

S00 prepares the repository. It does not complete the 28 screens or supersede B00–B02. B00 materializes and validates source specifications; B01 chooses compatible versions and installs dependencies; B02 completes the runnable CAP/UI5 shell. If S00 already created a compatible file, later prompts inspect and extend it rather than regenerate it.

## 4. Responsibilities and dependency direction

| Area | Owns | Must not own |
| --- | --- | --- |
| UI5 views, controllers and extensions | Presentation, user interaction, local selection, navigation and accessible feedback | Sole authorization, business approval decisions or database access |
| UI5 service wrappers | Calling CAP OData/action contracts and handling responses | Direct calls to five real SAP systems or secrets |
| CAP service implementations | Boundary validation, authenticated context, policy invocation, transactions and API contracts | Large duplicated workflow logic in every handler |
| Domain modules | Pure rules, graph/value validation and proposal invariants | UI controls or HTTP request state |
| Workflow | Allowed transitions, readiness, exact-version approval and invalidation | Fake success based on navigation |
| Agent runners | Bounded plans, deterministic proposals, citations and handoffs | Self-approval, arbitrary scripts or arbitrary endpoint access |
| Execution | Approved dispatch, action keys, target locks and reconciliation | Blind retry of unknown writes |
| Mock adapters | Deterministic external responses and capability declarations | Production credentials or implied live SAP support |
| Repositories | Scoped persistence and transactional data access | Duplicated JSON copies that disagree with CAP entities |
| Evidence and exports | Redacted lineage and authorized real downloads | Restricted data exposure or fabricated completion evidence |

Recommended call flow:

`UI5 action → CAP service → policy/readiness → domain/workflow → repository or typed adapter → evidence → response → UI feedback`.

Use repository wrappers only where they provide meaningful scope, persistence or query behavior. Avoid a mandatory interface/factory class for every CDS entity. Keep transaction ownership in the CAP request/workflow boundary and pass the transaction context into repository operations. Avoid nested transactions that silently split a business change.

## 5. SAP conventions and project choices

### CAP discovery and service implementation

- Retain `db/` and `srv/` as model roots. Verify that the chosen CAP version discovers models in the proposed nested folders and binds each `.cds` service to its actual `.js` implementation.
- Prefer matching service model/implementation basenames. Register handlers through supported CAP APIs. Add a compile-and-service-discovery check rather than assuming a filename causes registration.
- Use **one** custom `server.js` only if lifecycle customization is required. CAP supports a project-local root or `srv/server.js` bootstrap [S4]; do not create competing root and `srv` bootstraps.
- Do not create an Express application that bypasses CAP identity, service authorization or OData semantics merely to simplify the prototype.
- Use CDS schema/domain modules as the source of entity contracts. Generate metadata/types where appropriate; do not hand-maintain several incompatible copies of the same model.

### UI5 structure

`app/grow` is the frontend project root; its UI5 application sources live in `app/grow/webapp`. The manifest, component and application views belong there. SAPUI5 documents this `webapp` organization and its nested test area [S2].

Freestyle XML views/controllers and Fiori elements extensions coexist only where needed. A Fiori elements page generated by manifest configuration does not also need a duplicate freestyle screen. Record the chosen floorplan for each P00–P27 route in `docs/architecture/routing-and-floorplans.md`.

Start with native UI5 controls and supported extension APIs. Do not create a generic home-grown control library or internal DOM overrides. Keep `css/style.css` small and token-based. Use one application namespace, proposed `com.ey.grow.prototype`; replace `ey` with the approved organization namespace if required, once, with consistent manifest/resource mappings. A namespace is a naming choice, not permission to use EY branding.

### JavaScript and type discipline

Use JavaScript consistently for the initial CAP/UI5 prototype, with JSDoc and editor type checking where supported. Preserve UI5's supported module conventions and the selected CAP runtime's supported module system; do not mix incompatible ESM/CommonJS assumptions. Tooling scripts can use `.mjs` deliberately.

A TypeScript conversion is optional and requires an explicit decision and compiler/tooling setup. Do not introduce half-converted `.ts` files while the rest of the build expects JavaScript.

### Local persistence

Recommended local implementation: CAP with the supported SQLite adapter and a **file-backed** demo database under `.runtime/`. CAP's SQLite setup defaults to in-memory development behavior unless configured otherwise [S3]. Therefore restart persistence must be configured and tested, not assumed.

This selects a concrete local implementation of the earlier plan's persisted mock repository. Keep HANA-compatible CDS and test the later HANA migration separately. SQLite behavior is not proof of HANA Cloud compatibility, scaling or production recovery.

`docs/spec/*.json` are canonical source specifications. `fixtures/` are curated deterministic demo inputs. `.runtime/demo.sqlite` holds mutable demo state. They have separate purposes. Do not reload fixtures on every request or restart, which would erase approval history.

Use an explicit idempotent seed command and a confirmed scoped reset. Seed only an empty workspace unless reset is requested. Test pipelines may use a fresh in-memory or isolated temporary database, separate from presenter state.

### Development networking

Use CAP on a documented local backend port and UI5 tooling on a documented frontend port, proposed 4004 and 8080. Proxy `/odata/` and any deliberately exposed local health/download endpoints to CAP so the browser sees the frontend origin.

Use supported UI5/Fiori development middleware and pin its compatible package version. SAP documents middleware-backed backend proxying [S5]. Do not disable browser security, TLS verification or global CORS checks. Never configure mock integration fixtures to call real SAP tenants.

## 6. Dependency and configuration management

Use one root `package-lock.json` with npm workspaces containing `app/grow`. The root owns CAP and repository-wide verification scripts. The private UI5 workspace owns its UI build/run configuration. Install from the root; do not add a second child lockfile unintentionally.

| File | Guidance |
| --- | --- |
| Root `package.json` | `private: true`; workspace `app/grow`; root scripts; compatible Node engines selected in B01 |
| UI workspace `package.json` | `private: true`; distinct package name; UI5 scripts/dependencies appropriate to the chosen setup |
| `.nvmrc` | Supported Node major chosen from actual CAP/UI5 requirements, not an invented “latest” |
| `.npmrc` | Harmless repository preferences; no registry passwords or tokens |
| `.cdsrc.json` or `cds` block | Choose one main source for CAP settings and profiles; avoid conflicting duplicated declarations |
| `.env.example` | Nonsecret names/defaults only; document which are read by CAP or a script |
| `.env`, `.cdsrc-private.json` | Ignore; never commit real service bindings or credentials |
| `ui5.yaml` | App metadata, framework libraries and supported development/build middleware |
| `ui5-local.yaml` | Optional intentional alternate profile; not a copied conflicting configuration |

The default prototype profile must not permit live outbound SAP writes or infer production authentication from a browser-supplied role header. Demo identity is explicitly development-only and verified by the mock backend's session/context mechanism.

## 7. VS Code configuration

Open the **single repository root** rather than `app/grow` alone. This keeps CAP models, specifications, tests and repository instructions visible. A multi-root workspace is unnecessary for this prototype; VS Code supports normal folder workspaces and `.vscode` task/debug settings [S6].

### Recommended extension categories

Recommend SAP CDS language support, SAP Fiori tools/UI5 development support, ESLint, a formatter, YAML/JSON support and the Codex extension appropriate to the developer's environment. Validate exact extension identifiers in the current marketplace before adding them to `extensions.json`; do not invent IDs or auto-install global extensions. Add Playwright tooling only if that test runner is selected.

### Settings

- Honor `.editorconfig`; use LF and UTF-8, insert final newlines, trim trailing whitespace where appropriate.
- Use a formatter compatible with JavaScript, JSON, YAML and XML; configure per language rather than assigning a JSON formatter to XML.
- Enable supported code diagnostics and formatting on save without treating every formatting rule as a business gate.
- Exclude `.runtime`, generated build output, dependencies and raw test artifacts from normal search/watch where useful. Keep source, fixtures, spec and code tests searchable.
- Do not hide failures by excluding actual source folders from diagnostics.

### Tasks and debugging

| Configuration | Intended use | Enable when |
| --- | --- | --- |
| Verify repository structure | `npm run verify:structure` | S00 implements the real script |
| Materialize specification | `npm run spec:materialize` | B00 implements safe extraction |
| Verify specification | `npm run verify:spec` | B00 validation exists |
| Start CAP | Root `dev:backend` | B02 runnable service exists |
| Start UI5 | Root `dev:frontend` delegating to UI workspace | B02 UI/proxy exists |
| Start full prototype | Root `dev` with both child processes | B02 implements lifecycle and readiness |
| Debug CAP | Node/npm launch with child-process debugging | Runtime path and startup script are verified |
| Debug browser | Supported browser debugger to local UI URL | UI server and supported debugger available |
| Compound debug | CAP plus frontend/browser | Dependencies/startup readiness are configured |

Do not create an attractive but nonfunctional task list. During S00, include only working preparation tasks. Record future debug/task definitions in the guide and add them when their actual commands exist in B01/B02. An empty `launch.json` configurations array with an explanatory README note is acceptable scaffolding; a fake app entrypoint is not.

## 9. Test and evidence organization

UI5-native unit/OPA tests live under `app/grow/webapp/test`. Repository `test/` owns backend policy/domain/contracts and cross-stack journeys. If Playwright is chosen, keep its page objects and browser flows in `test/e2e`; do not run the exact same journey in three frameworks just to increase test counts.

UI tests should prefer accessible roles/names, stable application IDs and supported UI5 interaction techniques. Avoid brittle selectors against private generated DOM. Cover invalid state and access denial as well as happy paths.

`docs/qa` stores concise, versioned summaries and action/feature mappings. `artifacts/` stores generated reports, screenshots, traces and raw coverage, normally ignored in Git. CI may retain them as access-controlled job artifacts. `.runtime/` never becomes a source-data or audit archive.

The action registry needs fields such as action ID, screen, UI handler reference, permission, prerequisite, expected result and test ID. Separate:

1. 130 named screen actions;
2. 24 shared interaction families;
3. every rendered actionable instance in supported states;
4. 138 R1 feature representations;
5. actual future production implementation.

Do not present the first two counts as a complete denominator for all clickable UI elements.

## 10. Source ownership and Git rules

| Location | Source or generated | Commit guidance |
| --- | --- | --- |
| `docs/spec` | Canonical extracted source specification | Commit reviewed versions and provenance |
| `fixtures` | Synthetic deterministic inputs | Commit; exclude secrets and real client personal data |
| `db`, `srv`, UI5 sources | Application code/models | Commit after meaningful checks |
| `docs/reference` | Controlled source documents | Store only if permitted; use approved external references for restricted documents |
| `.runtime` | Mutable local state/uploads/exports/logs | Ignore |
| `artifacts`, `gen`, UI5 `dist`, `coverage` | Generated output | Ignore; retain required evidence through approved CI/review channels |
| `package-lock.json` | Reproducible dependency resolution | Commit after real npm resolution |
| `node_modules` | Installed packages | Ignore |

At minimum ignore `node_modules/`, `gen/`, `app/grow/dist/`, `.runtime/`, `artifacts/`, `coverage/`, test runner outputs, `*.log`, `.env`, `.env.*` except `.env.example`, `.cdsrc-private.json`, `default-env.json` and local credential/certificate files. Review patterns to avoid accidentally excluding safe templates or legitimate source fixtures.

Do not create a restrictive or open-source license on the user's behalf. Add a license only when the intended ownership and distribution terms are provided. Avoid committing proprietary reference documents merely because a repository exists.
